# `tmem_ffa.ko` → `ffa_v10` contract

## 1. Consumed exports: 1 of 5

`ffa_v10` exports five symbols (`ffa_driver_register`, `ffa_driver_unregister`,
`ffa_device_register`, `ffa_device_unregister`, `ffa_device_is_valid` — see
`phase4-ffa-v10-reconstruction.md`). `tmem_ffa` imports exactly **one**:

| symbol | stock CRC | provenance in rebuild | call site |
|---|---|---|---|
| `ffa_driver_register` | `0x0d53cde9` | **NATURAL** — genksyms output of the real source-built `//lieppos/ffa-v10` | `tmem_register_ffa_module` |

`ffa_driver_unregister` is **not** imported: the module never unregisters its
FF-A driver (it has no module_exit teardown of the FF-A side). Do not assume
the full `ffa_v10` surface is used.

## 2. Registration lifecycle

```c
static struct ffa_driver tmem_ffa_driver = {
        .name     = "tmem_ffa",
        .probe    = tmem_ffa_probe,
        .remove   = tmem_ffa_remove,
        .id_table = tmem_ffa_device_id,
};

int tmem_register_ffa_module(void)
{
        ret = ffa_register(&tmem_ffa_driver);      /* -> ffa_driver_register */
        if (ret) { pr_info("%s: failed to get FFA-ops\n", __func__);
                   return TMEM_KPOOL_FFA_INIT_FAILED; }
        ...
}
```

- On probe: `tmem_ffa_dev = ffa_dev; tmem_ffa_ops = ffa_dev->ops;` — the
  module keeps the partition device and its ops vector.
- On remove: no-op (`(void)ffa_dev;`).
- Failure is non-fatal to module load but makes every FF-A-backed allocation
  fail with `TMEM_KPOOL_FFA_INIT_FAILED`.

## 4. Memory operations

`tmem_ffa` uses the FF-A **memory** interface through `tmem_ffa_ops`, not
direct messaging:

| operation | evidence |
|---|---|
| share / lend | `"page-based, failed to FF-A send the memory, ret=%d"` on the alloc path (`tmem_ffa_page_alloc`, `ssheap` blocks) |
| reclaim | `"page-based, handle=0x%llx failed to FF-A reclaim, ret=%d"` on the free path |
| handle storage | `u64 ffa_handle` inside `struct ssheap_buf_info`; carve-out pools keep per-region handles |
| handle → PA | `tmem_query_ffa_handle_to_pa()` and the export `trusted_mem_ffa_query_pa` (consumed by `mtk_sec_heap` and `mali_kbase`) |
| region pools | `tmem_carveout_create/destroy` build `gen_pool` instances over FF-A-backed ranges (`tmem_ffa_region_alloc/free`) |

No FF-A **direct messaging** (`ffa_ops->msg_ops`) call sites exist in the stock
binary — the only `__arm_smccc_smc` use is in the SSMR/SMC path, not FF-A
messaging.

## 5. Error behaviour

| failure | behaviour |
|---|---|
| `ffa_register` fails | log, return `TMEM_KPOOL_FFA_INIT_FAILED`, FF-A backend stays unusable |
| FF-A send fails during page alloc | log, unwind the ssheap blocks, return allocation failure |
| FF-A reclaim fails during free | log with the handle value; memory is not returned to the pool |
| handle→PA query fails | `"%s fail: handle=0x%llx, idx=0x%lx"`, caller gets 0 |

## 6. Provider provenance

The FF-A edge is the **only** provider edge of `tmem_ffa` that is fully
source-natural today: `ffa_v10` is `DIRECT_SOURCE_MATCH / FROZEN FOR RE` and
its `ffa_driver_register` CRC `0x0d53cde9` is regenerated by genksyms from
MediaTek's own C, not copied from a stock ELF.
