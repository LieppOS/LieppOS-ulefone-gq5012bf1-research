The overlay matters. The base DT has the `extcon-usb` node but omits the four board GPIO properties. The DTBO adds `status = "okay"`, `id-gpios`, `otg_gpio_select`, `uvc_switch_gpio`, and `uvc_vbus_gpio`. The resulting properties match live `/proc/device-tree/extcon-usb`, so base-DTB-only analysis is incomplete.

## Controller topology

```text
/soc/usb0@11201000                         phandle 0xe3
  compatible = "mediatek,mtu3"
  reg = 0x11201000/0x2e00 (mac), 0x11203e00/0x100 (ippc)
  dr_mode = "otg"
  maximum-speed = "high-speed"
  usb-role-switch
  phys = <&u2port0 3>
  |
  +-- port/endpoint (0x146)
  |      <----------> /extcon-usb/port/endpoint (0xfa)
  |
  +-- /soc/usb0@11201000/xhci0@11200000    phandle 0xf8
         compatible = "mediatek,mtk-xhci"
         reg = 0x11200000/0x1000
         status = "okay"
```

The endpoint graph proves that `extcon-usb` controls the role of this exact `usb0` instance. No endpoint connects `extcon-usb` to a second controller.

## PHY topology

```text
/soc/usb-phy0@11f40000
  compatible = "mediatek,xsphy", "mediatek,mt6878-xsphy"
  reg = 0x11f40000/0x400
  reg-names = "u2_port_base"
  |
  +-- usb2-phy0@11f40000                   phandle 0xe2
        #phy-cells = <1>
```

`usb0@11201000` references only `<0xe2 3>`, which resolves to the USB2 PHY child above. The MT6375 charger node references that same PHY as `phy-names = "usb2-phy"` and references the MTU3 node as `usb = <0xe3>`.

There is no enabled `usb3-phy`, `u3phy`, or SuperSpeed PHY child in the production path. A separate root node exists:

```text
/usb-phy
  compatible = "mediatek,fpga-u3phy"
  status = "disabled"
```

That disabled FPGA-development placeholder has no connection to `usb0` and is **not** evidence that this PCB or production MT6878T instance has an enabled/routed USB3 PHY.

## USB3 DT classification

| Question | Result | Evidence |
|---|---|---|
| `USB3_DT_PRESENT` | **NO for an operational production path** | MTU3 is capped at `maximum-speed = "high-speed"`; only the U2 PHY is referenced. |
| `USB3_PHY_NODE_PRESENT` | **YES only as a disabled FPGA placeholder; NO enabled production U3 node** | `/usb-phy` is `mediatek,fpga-u3phy`, `status = "disabled"`. |
| `USB3_PHY_ENABLED` | **NO** | No enabled U3 PHY node/reference. |
| `USB3_CONTROLLER_ENABLED` | **NO for SuperSpeed operation** | MTU3/xHCI are enabled but configured with only the U2 PHY and High-Speed ceiling. |

This says what stock DT configures. It does not settle whether the MT6878T silicon contains dormant USB3 IP or whether the board routes SS pairs.

## Role, VBUS and board routing controls

The effective `/extcon-usb` node is:

- `compatible = "mediatek,extcon-usb"`;
- endpoint-linked directly to MTU3 `usb0`;
- `tcpc = "type_c_port0"`;
- `charger = <0xe4>` (MT6375 charger);
- `vbus-supply = <0x145>` (`usb-otg-vbus` regulator);
- `vbus-voltage = 5,250,000 uV`;
- `vbus-current = 1,800,000 uA`;
- `vbus-limit-current = 500,000 uA`;
- GPIO 28: `id-gpios` / accessory detection;
- GPIO 37: `otg_gpio_select` / Type-C source-VBUS companion selection;
- GPIO 55: `uvc_switch_gpio` / UVC-USB route switch;
- GPIO 152: `uvc_vbus_gpio` / internal accessory power/VBUS.

The GPIO meanings are supported jointly by the effective DT and the stock `extcon-mtk-usb.ko` reconstruction/oracle in `kernel/phase4-extcon-mtk-usb-*`. Software proves that these controls exist; it does not reveal the PCB netlist behind the switch.

The MT6375 charger node `/soc/i2c@11280000/mt6375@34/chg` contains the `usb-otg-vbus` regulator (4.85–5.50 V, 0.5–2.4 A), references the same USB2 PHY and MTU3 controller, and supplies `extcon-usb`.

## Type-C/PD DT node

`/soc/i2c@11280000/mt6375@34/tcpc` is integrated below the MT6375 MFD at I2C controller `11280000`, address `0x34`:

- `compatible = "mediatek,mt6375-tcpc"`;
- interrupt `0x78`, name `pd_evt`;
- `tcpc,name = "type_c_port0"`;
- dual-power-role and dual-data-role capabilities (`local-dr-power`, `local-dr-data`);
- `local-usb-comm`;
- PD vendor/product data `0x29cf:0x6375` and manufacturer `RichtekTCPC`;
- Type-C receptacle/DisplayPort capability data is present.

`/soc/typec-mux-switch` is enabled with `compatible = "mediatek,typec_mux_switch"` and the overlay adds `orientation-switch`, `mode-switch`, `accessory` plus an endpoint linked to the MT6375 TCPC endpoint. It has no endpoint or phandle to MTU3, an enabled SuperSpeed PHY, a named redriver/retimer IC, or connector lane nodes. It therefore proves that the stock Type-C policy stack exposes orientation/mode switching, but cannot be promoted into proof of SS-lane or DisplayPort copper routing.

## Internal thermal-camera DT nodes

Two separate glue functions are visible:

1. `/yft_tiny2c_usb`, `compatible = "mediatek,yft_tiny2c_usb"`, controls three rails through GPIOs 192, 191 and 149 (`1v8`, `3v3`, `vddio_3v3`).
2. `/soc/i2c@11e03000/fm78100@0x3c`, `compatible = "mediatek,tiny2c_usb"`, is enabled at I2C bus/address `8-003c` in Linux numbering.

Neither node is a USB host controller, USB device or bridge. The `extcon-usb` node owns the USB role plus GPIO 55 route switch and GPIO 152 accessory power. This makes one shared MTU3/USB2 fabric the **strongly supported** internal-camera route, but the exact downstream physical switch/net and runtime USB port number still require powered-camera enumeration.

## Controller count

The merged stock DT contains one operational MTU3 node (`/soc/usb0@11201000`) and one xHCI child (`11200000.xhci0`). There is no live `11211000.usb1` or `11210000.xhci` node. Old init/fstab references to `11211000.usb1` are dead userspace remnants, not controller evidence.

Classification: **PROVEN for this effective stock DT**. This does not exclude undocumented silicon IP that the board DT never instantiates.
