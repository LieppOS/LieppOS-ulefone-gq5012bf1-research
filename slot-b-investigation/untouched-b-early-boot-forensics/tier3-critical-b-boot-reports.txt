## Refined classification

The strongest remaining boundary is:


selector-contract failure. Possible proprietary inputs include:

- Preloader_b/LK_B boot-source state;
- slot-B parameter handoff into the shared BL2 extension;
- UFS boot-LUN/partition identity assumptions;
- slot-specific certificate/DICE/RPMB state;
- an OEM design where `lk_b=NONE` is intentional and Android B was not meant to
  select a secondary LK path.

Both candidates use the same `bl2_ext`, main LK DTB, and LK DTBO payloads. The
current experiment also controls for main `lk`/`aee` generation. Ordinary
Android boot, AVB descriptor, kernel, first-stage init, and userspace debugging
remain downstream and unobservable.

## Why this is stronger than an LK-image hypothesis

Both factory V15 and exact working-A LK containers use the same `bl2_ext` and
produce the same slot-B `LK_CRASH(BL2_EXT)`/USB pattern. Static ARM64 analysis
shows the shared BL2 extension:

- reads standard `boot_control` metadata;
- returns `_a` or `_b` from `get_suffix`;
- validates both suffixes;
- constructs partition names with `%s%s`;
- contains `preloader_a` and `preloader_b` paths.

Working A then loads these suffixed partitions in order:

```text
lk, logo, gz, tee, sspm, pi_img, mcupm, dtbo, scp, ccu,
spmfw, apusys, dpm, modem, gpueb, vcp,
connsys_bt, connsys_gnss, connsys_wifi
```

Factory scatter assigns an A image to every one but marks every corresponding B
entry `NONE`/not-downloadable. Current work has populated only `lk_b` and
`dtbo_b` from this BL2 chain. Seventeen subordinate B firmware partitions were
never provisioned.

`logo_b` is the first unprovisioned load but may be nonfatal. `gz_b` is the
first likely mandatory image; BL2 strings include fatal/explicit geniezone load
failure paths. `tee_b`, SSPM/SCP and later co-processor images also follow.

This can explain why two coherent LK generations both enter BL2_EXT and fail in
the same way.

## Approved live hash result

The separately approved helper hashed all 17 A/B pairs from healthy A without
retaining raw bytes. Every B partition hash equals the independently generated
all-zero hash for its exact capacity; every A hash is nonzero and differs from
B.

```text
B_ALL_ZERO_COUNT=17/17
fastboot commands=0
reboots=0
setters=0
writes=0
```

This converts the suspect into a deterministic cause: BL2_EXT constructs `_b`
partition names, but every subordinate B firmware image it needs is absent.
The first unprovisioned working-A load is optional-looking `logo`; the first
likely mandatory load is `gz`.

## Source-provenance result

A second separately approved read-only helper hashed the exact factory-image
length prefix from every working A partition. Result:

```text
FACTORY_V15_PREFIX_MATCHES=0/17
SOURCE_DECISION=SAME_DEVICE_WORKING_A_PRIVATE_CAPTURE_REQUIRED
```

Thus the mismatch is not only partition-tail padding: all 17 installed image
prefixes differ from factory V15. The installed older preloader/LK/subordinate
firmware set is the only selector generation proven to boot on this phone.

No provisioning is authorized. The next possible step is a separately reviewed
private capture of the 17 exact working-A partitions for format/active-length,
certificate, and B-capacity analysis. A future complete B firmware set would
require exact candidate derivation, one separately approved provisioning gate,
returned-A readback, and no B boot in the same transaction.

## Convergent proof

### 1. Factory selector layout

Factory V15 scatter declares:

| Stage | A | B |
|---|---|---|
| UFS preloader | `preloader_k6878v1_64.bin`, download `true` | same image, download `true` |
| LK | `lk.img`, download `true` | `NONE`, download `false` |

The two live 4 MiB UFS preloader LUs are byte-identical:

```text
sda = ebbb4691a570b2dcd6ba8d6f66de5007fc148e802c764aebc16183bfee7ec63c
sdb = ebbb4691a570b2dcd6ba8d6f66de5007fc148e802c764aebc16183bfee7ec63c
```

Therefore the B preloader implementation itself is present and paired with A.
The missing stage is the next B bootloader partition.

### 2. Live LK partitions

Read-only full-partition hashes are:

```text
lk_a bytes  = 16777216
lk_a sha256 = ee0303f531e204f639a9e2f4f058ffd1ae159b02804c402282a9def15d250461

lk_b bytes  = 16777216
lk_b sha256 = 080acf35a507ac9849cfcba47dc2ad83e01b75663a516279c8b9d243b719643e
```

`080acf...` is independently recomputed as SHA-256 of exactly 16,777,216 zero
bytes. Thus `lk_b` is not merely invalid or stale: it contains no LK image at
all. `lk_a` is populated and is the stage used by working A.

### 3. Surviving PL/LK buffer proves the successful A path

The 174,993-byte `/proc/pl_lk` buffer contains the final returned-A boot only.
Its relevant sequence is:

```text
[AB] Current boot: Preloader_a
[AB] ab_suffix: _a, ab_retry: 1
[PART] partition name = lk_a
[PART] load "lk_a" ... [SUCCESS]
Load 'lk_a' partition ... (899056 bytes ...)
lk finished --> jump to linux kernel 64Bit
```

Factory preloader strings contain symmetric `Preloader_a` and `Preloader_b`
paths, suffix/retry handling, and boot-control persistence. The successful A
trace demonstrates the selector relationship: selected preloader suffix `_a`
loads `lk_a`; the symmetric B path has only a zero-filled `lk_b` available.

The failed B PL/LK bytes did not survive in `/proc/pl_lk`; the final A boot
replaced that volatile buffer. This prevents quoting the exact failed-B
preloader error line, but does not restore a plausible later Android boundary.

### 4. Timestamp-matched AEE classification

`db.fatal.03.KE/ZZ_INTERNAL` states:

```text
PL_CRASH, Wed Aug 12 12:49:29 EEST 2026
```

That is `2026-08-12T09:49:29Z`, 119.300 seconds after the one approved B reboot
and 20.925 seconds before returned A was observed. `db_history` records the same
class and timestamp. Earlier B-selector episodes also created `.01` and `.02`
records classified `PL_CRASH`.

The authoritative factory `aee_aedv64_v2` binary has separate labels for
`Exception Type: PL_CRASH` and `Exception Type: AEE_LK_CRASH`. Therefore the
`.03` label is preloader evidence; the `db.fatal.*.KE` directory name does not
prove Linux kernel entry.

The 2,458,919-byte `.dbg` payload was preserved privately and hash-verified but
is encrypted/high-entropy. It was not decrypted, and raw `expdb` was not read.

### 5. Retry chronology

The diagnostic attempt independently proved:

```text
B tries:              7 -> 0
BROM enumerations:    7
preloader enumerations: 9
mean retry period:    10.480 s
A fallback:           proven after retry exhaustion
```

A zero-filled `lk_b` explains the complete sequence without invoking any
Android image: each B selection reaches preloader, cannot establish the B LK
stage, resets through BROM, decrements the normal retry count, and eventually
returns to the populated A selector chain.

## Classification decision

The Phase 5 completion route is now:

```text
A. deterministic pre-kernel/bootloader cause proven offline
```

Primary classification is `BOOTLOADER_SLOT_CONTROL_FAILURE`; machine root
cause is `LK_B_ALL_ZERO`. `BOOT_IMAGE_PARSE_FAILURE` is not used because the
failure occurs before LK can parse Android `boot_b`, `vendor_boot_b`, or their
AVB metadata.

The earlier `UNKNOWN_PRE_ADB` result remains historically correct for the
immediate diagnostic capture. It is superseded by the deferred evidence, not
rewritten in the immutable attempt artifacts.

## Remaining limitation

The exact failed-B preloader printf/return code is unavailable because:

- `/proc/pl_lk` retained only the final A boot; and
- the AEE `.dbg` payload is encrypted and no raw `expdb` read was authorized.

This warrants `PASS_WITH_LIMITATION`, not `INCOMPLETE_SAFE`. Independent
factory layout, full live hashes, `PL_CRASH`, selector symmetry, and retry
chronology all converge on the missing `lk_b` stage.
