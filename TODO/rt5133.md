# RT5133 Future Checkout Notes

## Device

- **Phone:** Ulefone Armor 29 Pro Thermal
- **Board / product:** GQ5012BF1
- **Project:** LieppOS
- **Component:** Richtek RT5133 / RT5133A regulator / GPIO expander
- **Current conclusion:** **Not active on this board. Do not enable blindly.**

## Current verified state

The stock device tree contains an RT5133 node inherited unchanged from the MediaTek MT6878 base DT:

- Compatible: `richtek,rt5133`
- Bus: **I2C5**
- Address: **0x18**
- IRQ: **EINT19**, falling edge
- HWEN: **GPIO1**
- Bus transfers use an additional **CRC-8, polynomial 0x07**

The driver recognizes two silicon IDs through `CHIP_INFO[7:4]`:

- `0x7` = RT5133
- `0x8` = RT5133A

The reference DT configuration appears intended for **RT5133A**, based on the regulator voltage tables.

On GQ5012BF1, the module loads during first-stage boot but its probe fails on the first CRC-checked read of register `0x00`.

Result:

- **0 / 9 regulators register**
- **0 / 3 GPOs register**
- IRQ is never requested
- no RT5133 consumer becomes active
- live sysfs showed `5-0018` without a bound driver

Software evidence cannot currently distinguish between:

1. the RT5133/RT5133A footprint being physically unpopulated, or
2. the IC being present but unpowered / disconnected / otherwise inaccessible.

## Important GPIO conflict

**GPIO1 must not be claimed by RT5133 without first checking the PCB.**

On this phone GPIO1 is reused by the **WL2864C camera power IC** as its reset/control GPIO.

Current stock behavior is safe because RT5133 probe fails and releases GPIO1 before the WL2864C driver claims it.

If RT5133 were made to probe successfully without changing the hardware/DT arrangement:

1. RT5133 would retain GPIO1.
2. WL2864C would attempt to request GPIO1.
3. WL2864C could fail with `-EBUSY`.
4. Camera power rails could fail.

Therefore:

> **Do not “fix” or force RT5133 probe success in software on the existing board configuration.**

## What RT5133 would provide if physically usable

The driver supports:

- **9 regulator outputs**
- **3 GPO outputs**
- programmable voltage selection
- output enable / disable
- fault/status handling
- over-current / power-good notification paths
- reset / shutdown configuration

However, none of those outputs currently have a proven consumer on GQ5012BF1.

No active phone subsystem references RT5133 rails. It is **not** part of the active MT6369 codec, AW88394 speaker, headset/earpiece, microphone-bias, or camera power paths. The camera LDO on this board is **WL2864C**, not RT5133.

## What features would enabling it add?

### On the current unmodified phone

**Probably none.**

Even if the chip is physically present, no current DT consumer references its regulator outputs.

A functioning RT5133 would only become useful if its outputs are physically routed to usable PCB nets and those nets can safely power additional hardware.

Possible future value, *if proven by teardown/schematic tracing*:

- extra software-controlled regulator rails
- additional switched power outputs
- extra GPO control signals
- power supply for custom internal hardware mods

These are possibilities only. None are currently proven to be routed on GQ5012BF1.

## Recommended future checkout

A future hardware inspection should answer the following before any software change.

### 1. Is the IC physically populated?

Locate the presumed RT5133/RT5133A footprint near the relevant I2C/power circuitry.

Record:

- package markings
- package type
- populated / unpopulated
- surrounding passives
- enable/power input connections

Photograph both sides of the PCB at high resolution.

### 2. Verify whether I2C5 reaches the footprint

Trace / measure continuity for:

- SDA
- SCL
- ground
- VIN
- HWEN / GPIO1

Do not power the board specifically for this investigation until the net topology is understood.

### 3. Trace regulator outputs

For each RT5133 output, determine whether it is:

- routed nowhere
- routed to a test pad
- routed to an unpopulated option
- routed to an active device
- shared with another regulator
- connected to an expansion / accessory circuit

### 4. Resolve GPIO1 ownership

Before ever enabling RT5133, determine whether GPIO1 can be reassigned without breaking WL2864C.

Possible outcomes:

- RT5133 footprint is absent → disable/remove stale node.
- RT5133 exists but HWEN is not actually GPIO1 on this PCB → correct DT.
- RT5133 and WL2864C share GPIO1 electrically → investigate intended sequencing before changing anything.
- RT5133 exists on an optional variant only → keep disabled on GQ5012BF1.

### 5. Only after hardware proof

If RT5133 is physically present and useful:

- create a board-specific DT node rather than relying on inherited reference-board data
- assign only verified consumers
- resolve the GPIO1 conflict first
- validate one regulator at a time
- start with conservative voltage limits
- verify camera power still works
- preserve an easy rollback path

## Register notes

Known driver register groups include:

- chip information: `0x00`
- software reset: `0x06 = 0xB1`
- base enable: `0x09`, bit 1, inverted
- GPO outputs: `0x0B`
- fault event / mask groups: `0x10–0x12`, `0x16–0x18`
- shutdown policy: `0x19`
- per-LDO enable: `LDOn_CTRL1`, bit 7
- per-LDO voltage selection: `CTRL2`, bits 7:5

On the actual GQ5012BF1 board, the only observed attempted access is the failed initial read of register `0x00`.

## Stock-driver quirks

Two latent bugs were found in the stock driver:

1. `remove()` unregisters the debug device twice.
2. an unknown die ID can lead to a NULL dereference.

Neither is reachable on the current GQ5012BF1 because probe fails immediately.

A separate regulator-framework issue means `regulator-active-discharge` is effectively ignored with this stock implementation because a valueless DT property is read as a numeric `u32`.

## LieppOS recommendation

For the current hardware configuration:

**Prefer disabling/removing the stale RT5133 node/module rather than trying to make it bind.**

Reasons:

- no active consumer exists
- probe currently fails harmlessly
- GPIO1 is needed by WL2864C
- successful RT5133 binding could break camera power
- no user-facing feature is currently gained

Revisit RT5133 only after a physical PCB inspection proves that the IC exists and that one or more outputs are usefully routed.
