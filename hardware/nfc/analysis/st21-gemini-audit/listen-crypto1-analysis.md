# Listen-A, UID/ATQA/SAK and Crypto1 path assessment

## Scope

Determine, from source + installed binaries + live device logs, whether any path enables
MIFARE Classic **card/PICC emulation** (Listen-A + Crypto1), as opposed to reader-side MIFARE
support or generic NFC-A/T2T listen.

## 1. The decisive live-device experiment (controller rejection)

Two on-device tests attempted to program `RF_DISCOVER_MAP_CMD` with a MIFARE (`0x90`)
mapping, differing only in the mode byte. NCI `RF_DISCOVER_MAP` mode bitmap: `0x01` = POLL,
`0x02` = LISTEN.

| Test | Tx command | Decoded | Rx response | Status |
|---|---|---|---|---|
| `analysis/mifare-090-poll-map-test.txt:396,399` | `21 00 07 02 04 03 02 90 01 90` | entry1 ISO-DEP poll+listen; entry2 MIFARE **POLL** iface `0x90` | `41 00 01 00` | **0x00 ACCEPTED** |
| `analysis/mifare-090-listen-map-test.txt:401,404` | `21 00 07 02 04 03 02 90 02 90` | entry1 ISO-DEP poll+listen; entry2 MIFARE **LISTEN** iface `0x90` | `41 00 01 01` | **0x01 REJECTED** |

**Interpretation:** the ST controller *accepts* MIFARE mapped to **poll** (reader) mode but
*rejects the identical mapping in listen mode*. The rejection is generated by the controller
firmware itself (RF_DISCOVER_MAP_RSP status byte), not by host policy. This is direct,
reproducible proof that the standard NCI discovery-map route cannot enable MIFARE Classic
PICC/card emulation on this controller/firmware. It does not logically exclude an entirely
undocumented vendor command; the separate command/config searches found no such command.

## 2. Source-level: normal CE API cannot request MIFARE listen

- `nfa/ce/nfa_ce_api.cc:116-153`: `NFA_CeConfigureLocalTag` rejects `NFA_PROTOCOL_MASK_T1T`
  and `NFA_PROTOCOL_MASK_T2T`, and rejects a supplied UID when a protocol mask is present.
- `nfa/ce/nfa_ce_act.cc:422-495`: NDEF CE adds only T3T + ISO-DEP listen masks.

MIFARE Classic is neither T3T nor ISO-DEP; the standard CE API has no field for it. See
`aosp-nci-listen-analysis.md §2`.

## 3. Source-level: low-level Listen-A exists but is T2T/NFC-A only

- `nfa_dm_int.h:341`: `NFA_DM_DISC_MASK_LA_T2T = 0x00020000` (a listen mask exists).
- `nfa_dm_discover.cc:350-400,460-510`: `nfa_dm_set_rf_listen_mode_config` /
  `..._raw_config` serialize `LA_BIT_FRAME_SDD`, `LA_PLATFORM_CONFIG`, `LA_SEL_INFO`,
  `LA_NFCID1` into CORE_SET_CONFIG. A zero platform/SEL config is classified **T2T**.

So the host *can* request fixed NFCID1 and Listen-A SENS_RES/SEL_RES bytes — but this is the
generic NFC-A / Type-2 listen surface. There is no Crypto1 state machine, no MIFARE sector
key handling, and (per §1) the controller refuses to enter a MIFARE listen interface anyway.

## 4. UID / ATQA / SAK control

- ATQA/SENS_RES = `LA_BIT_FRAME_SDD` (`0x30`) + `LA_PLATFORM_CONFIG` (`0x31`);
  SAK/SEL_RES = `LA_SEL_INFO` (`0x32`); UID/NFCID1 = `LA_NFCID1` (`0x33`)
  (`nci_defs.h:508-577`, `nfa_api.h:579-600`). Corrected from the false `0x22-0x27` claim.
- The host can serialize these values, but:
  - the normal CE API blocks the UID path (§2);
  - the §1 test disproves the complete MIFARE protocol/interface listen mapping, **not**
    acceptance of a generic Listen-A SEL_RES byte such as `0x08`; presenting MIFARE-looking
    anticollision bytes would still not implement the Classic authentication/data protocol;
  - `setForceSAK` in the alternative JNI sends `2F 0C 02 01 <en>` and **discards** the SAK
    integer argument (`vendor-command-table.md §3`), so it is not arbitrary-SAK control.

## 5. Crypto1: reader-side only

- Installed `libnfc_nci_jni.so` exports reader-side MIFARE symbols (`RW_Mfc*`,
  `nfa_rw_check_mifare_data`, `rw_mfc.cc` paths) and `nativeNfcTag_doConnect` selects
  interface `0x90` only when **connecting to a discovered tag** in poll/reader mode
  (`non-isodep-non-mifare-function.md`).
- No `ce_t2t` / card-side MIFARE / PICC Crypto1 emulation symbol is present.
- Crypto1 here is the reader authenticating *to* a card, never a card authenticating a reader.

## 6. HCI / NFCEE: active route is negative, alternative ST route is unresolved

### Active mainline stack

- HCI APIs (`NFA_Hci*`) manage gates, pipes, commands and events to embedded/UICC secure
  elements. They do not themselves implement a PICC protocol.
- Active `RoutingManager::updateDefaultProtocolRoute()` programs only
  `NFA_PROTOCOL_MASK_ISO_DEP` and `NFA_PROTOCOL_MASK_T3T`; it contains no MIFARE/Classic
  protocol route.
- Stock config routes ISO-DEP to UICC1 (`DEFAULT_ISODEP_ROUTE=0x81`) and explicitly disables
  NDEF NFCEE (`NDEF_NFCEE_ENABLE=0`, `blobs/libnfc-hal-st.conf:145-166`).
- The extra NFCEE code is explicitly **T4T** (`NativeT4tNfcee`, `RW_T4tNfcee*`,
  `T4T_NDEF_NFCEE_AID`) — ISO-DEP/Type 4, not NFC-DEP and not MIFARE Classic.

### Alternative `/system_ext` ST stack (not runtime-loaded)

A genuine off-host lead exists and must not be erased:

- Decompiled `NfcService.java` exposes preference `default_mifare_route` and passes it to
  `setUserDefaultRoutesPref(mifare, isoDep, felica, abTech, sc, aid)`.
- `libstnfc_nci_jni.so` has `StRoutingManager::setVarDefaultRoutes`,
  `checkIfUiccRoute`, and `updateEeTechRouteSetting`; strings include “Mifare route is UICC”.
- At VAs `0x160044-0x160078`, `updateEeTechRouteSetting` compares its stored MIFARE route
  against each NFCEE handle and derives a technology mask; at `0x160138` it calls
  `NFA_EeSetDefaultTechRouting`. Exact evidence is in
  `evidence/alternative-mifare-offhost-route.txt`.

This is **STATIC IMPLEMENTATION** of an ST off-host MIFARE routing preference, but the binary
was not mapped in the observed NFC process. It does not prove that this phone's UICC/eSE
contains a MIFARE Classic applet or PICC-side Crypto1, nor does it provide arbitrary host
memory/keys. RF_DISCOVER_MAP governs DH interface mapping, so its `0x90`-LISTEN rejection does
not conclusively disprove a separate off-host technology route.

Runtime NFCEE IDs `0x81`, `0x82`, and `0x10` prove only that endpoints exist. Whether any
endpoint advertises and actually executes off-host MIFARE Classic is **UNKNOWN**.

## 7. Verdict

| Question | Finding | Evidence level |
|---|---|---|
| Does the controller allow MIFARE listen mapping? | **No — RF_DISCOVER_MAP listen rejected (0x01)** | PROVEN RUNTIME |
| Does the controller allow MIFARE poll mapping? | Yes (0x00) — reader side | PROVEN RUNTIME |
| Normal CE API expose MIFARE/T2T listen? | No — rejected in source | STATIC IMPLEMENTATION |
| Low-level Listen-A present? | Yes, but NFC-A/T2T only | STATIC IMPLEMENTATION |
| Arbitrary UID/ATQA/SAK for CE? | Not reachable / not accepted for MIFARE listen | STATIC + RUNTIME |
| HCI/NFCEE bypass present? | Active: no; alternative stack has unproven UICC MIFARE route | STATIC / UNKNOWN runtime |
| Card-side Crypto1 present? | Not found; only reader-side in active stack | NOT FOUND |

**Conclusion:** the active host stack has no MIFARE Classic CE surface, its visible MIFARE
implementation is reader-side, and the live controller rejects the standard DH MIFARE-listen
map while accepting poll mode. The alternative ST stack contains a meaningful off-host/UICC
MIFARE-route lead, but it was not loaded and no MIFARE-capable NFCEE applet or PICC Crypto1
execution is proven. Thus no **usable arbitrary host MIFARE Classic emulator** is established;
an off-host secure-element path remains unresolved rather than disproven.
