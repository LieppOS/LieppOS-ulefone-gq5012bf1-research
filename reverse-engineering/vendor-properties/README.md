# VENDOR-PROPERTIES — closure (2026-10-07, static)

Workspace component `Reverse Engineer - PARTIAL/VENDOR-PROPERTIES` → **DONE**.

## Scope

The stock vendor-side property surface means every key in:
* `vendor/build.prop`;
* `vendor/odm/etc/build.prop`;
* `vendor_dlkm/etc/build.prop`;
* `odm_dlkm/etc/build.prop`.

That is 747 distinct keys. For each one, this closure answers:
1. What is its stock value?
2. Which stock binaries consume it?
3. Does the LieppOS device/vendor tree reproduce it?

Runtime effect under enforcing SELinux is not in scope; that is ROM
integration.

## Result

`scripts/vendor_prop_diff.py` writes the per-key ledger
`evidence/vendor-property-ledger.tsv`, which has one row per key: value,
source file, class, consumer files, whether the key is in sepolicy contexts,
verdict, and any stock RC `setprop`.

**Consumers.** They are found by a byte scan (`rg -a -F`) of every stock
partition: vendor, odm_dlkm, vendor_dlkm, system, system_ext, product.
`*.prop` files are excluded, and sepolicy contexts files are counted
separately.

**Definitions.** A key counts as defined if it appears in the LieppOS
device and vendor trees: `*.mk`, `*.prop` and `*.rc`, excluding
`proprietary/` and `sepolicy/`.

| verdict | keys |
|---|---:|
| GENERATED by the build system (`ro.product.vendor.*`, `ro.vendor.build.*`, …) | 61 |
| DROP-SAFE: debug/log namespace, no stock consumer | 247 |
| DROP-SAFE: no stock consumer found | 67 |
| CHECK: normally supplied by inherited AOSP product makefiles (`ro.virtual_ab.*`, `dalvik.vm.*`, `bluetooth.profile.*`, …) | 29 |
| **MISSING from the LieppOS tree, with a stock consumer** | **343** |

**Main finding.** The current LieppOS device tree defines **no** vendor
properties. Stock `vendor/build.prop` and `odm/etc/build.prop` are
`EXTRACT_ONLY`, and there is no `TARGET_VENDOR_PROP`. A LieppOS vendor
image would therefore lose 343 consumed stock tunables, including:
* 179 `ro.vendor.*` MTK feature flags (read by `mtkfusionrild`, `em_hidl`,
  `mnld`, PQ, thermal and others);
* 37 `persist.vendor.*` (for example `persist.vendor.radio.msimmode`);
* SurfaceFlinger, `debug.sf` and `vendor.debug.*` knobs that have readers.

These keys and their stock values are emitted verbatim as
`evidence/lieppos-vendor-missing.prop`, ready to install as
`TARGET_VENDOR_PROP`/`TARGET_ODM_PROP` (an integration step).

**Contamination rule (unchanged, verified).** Build identity and attestation
values come only from stock `build.prop` files, never from the
property-contaminated live snapshot. See `notes/evidence-sources.md`.

## Declared limits

* Strings inside compressed APK/JAR members are not scanned. Their readers,
  such as EngineerMode, appear only when the APK stores the string
  uncompressed.
* A key counted as DROP-SAFE may still be read through dynamically built
  names (prefix + suffix).
* The 29 CHECK keys must be confirmed against the final product inheritance.
