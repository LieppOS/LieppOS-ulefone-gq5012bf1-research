# IMX989 (camera 0, rear main) — source donor analysis, mode map, kernel contract

## Identity (PROVEN)

* Runtime HAL: `[00] BACK SENSOR_DRVNAME_IMX989_MIPI_RAW`, orientation 90.
* Kernel bind: `imx989_mipi_raw` sub-driver of stock `imgsensor.ko`
  (`imgsensor_subdrvs[0]`). Its `get_imgsensor_id` reads 0x0016/0x0017 at
  write-ID 0x34 (7-bit 0x1A) and accepts only 0x0989 **and only if
  `is_yft_cts_board()==0`**; otherwise `imx989cts_mipi_raw` (expects
  0x0988) binds. So this handset's sensor answered chip-ID 0x0989 —
  this upgrades the earlier "STRONGLY_SUPPORTED IMX989" verdict to
  **PROVEN at the chip-ID register level** (a GN1 would return 0x08E1 and
  bind `s5kgn1sp_mipi_raw`, a GM2 0x08D2).
* DT: `i2c@11e02000` (i2c-7) `sensor0`, reg 0x20 (node address only),
  `sensor-names = imx989, s5kgm2sp, imx989cts, s5kgn1sp`; endpoint →
  `seninf-csi-port-3`.

Register-table result (`donor-comparisons/imx989-table-crossmatch.tsv`):
54 stock tables → **50 byte-identical** to a donor table;
init (295 pairs) identical; 23 of 24 seamless tables identical (custom7
re-uses donor `seamless_custom8`); **4 mode tables are stock-only**:

| stock mode | output | closest donor | delta |
|---|---|---|---|
| custom7 (idx 11) | 4096×2304 @60 | imx989 custom23 (243/269) | new PLL (0x0307/030B/030D/030E/030F), line/frame length, 0x38xx PD/readout timing |
| custom8 (idx 12) | 2048×1152 @60 | imx989lite custom21 (246/269) | PLL + 0x38xx timing |
| custom12 (idx 16) | 8192×6144 @15 | imx989lite custom16 (253/269) | **lower PLL (pclk 2.112 GHz, MIPI 987 Msps)** |
| custom20 (idx 24) | 7680×4320 @30 | imx989 custom20 (251/268) | PLL, 0x3205/0x3206 (QSC enable) =1 |

All four stock-only tables share one structural edit: donor writes
`0xB804/0xB83C/0xB874`, `0x0808`, `0x084E-0x0855`, `0x0858/0x0859`
(MIPI global timing/manual Tclk); stock replaces them with
`0x0860-0x0863`. These four modes are the low-MIPI-rate C-PHY variants.

## Mode map (33 modes; full TSV `donor-comparisons/imx989-mode-map.tsv`)

C-PHY 3-trio, MCLK 19.2 MHz, full array 8192×6144. Highlights:
preview/capture 4096×3072@30 (RAW10 + PD VC 0x30 4096×768),
normal_video 4096×2304@30, hs 1080p@120, slim 720p@240, custom1 2160p@30,
custom2 1080p@480, custom3 720p@480, custom12/13 full-res remosaic
8192×6144@15/24, custom20 7680×4320@30, DCG-compose (custom5/16/17),
stagger 2/3-exp (custom14/15), LBMF (custom6/18/28), DCG-raw
(custom24/25/26). Seamless groups 1 (4:3) and 2 (16:9).

**Stock defect (PROVEN, data-level):** modes 3, 4, 5, 13 have
`frame_desc` arrays that do not match their window (`hs_video` 1920×1080
but VC 4096×2304; `slim` 1280×720 → VC 1920×1080; `custom1` 3840×2160 →
VC 1280×720; `custom9` 4096×3072 → VC 3296×2460). The ODM re-ordered
setting tables/windows but kept the donor frame descriptors. The donor
object has 0 such mismatches. A reconstruction must decide whether to
reproduce stock byte-for-byte or fix it.

## Kernel contract (what a replacement must provide)

* `subdrv_entry` name `imx989_mipi_raw`, id 0x989, `ops` = framework
  `common_*` + per-TU `get_imgsensor_id` (CTS-gated), `init_ctx`, `open`,
  `vsync_notify`; static_ctx exactly as `stock-imgsensor-oracle/oracle.json`.
* Exposure 0x0202/03, gain 0x0204/05, frame length 0x0340/41, stream
  0x0100, mirror 0x0101, temperature enable/read 0x0138/0x013A,
  ana gain 1×–64×, exposure min 8 / margin 48, max FL 65528.
* Power: custom-LDO channels avdd=3, dvdd=2, dovdd=7, afvdd=5 (WL2864C);
  avdd2 = `camera-common-avdd2` regulator-fixed GPIO184; MCLK
  `CLK_TOP_CAMTG3_SEL` from `UVPLL192M_D10` (19.2 MHz), PDN/RST via pinctrl
  `cam0@0..3`.
* `imgsensor.ko` framework delta needed: `custom_ldo_ch[14]` in
  `adaptor_ctx` (`reconstruction/imgsensor-adaptor-ctx-custom-ldo-slot.patch`)
  + `set/unset_custom_ldo` (WL2868-CAMERA-LDO track has the LDO side).
